# Darkness II VR camera-shake source audit (2026-11-01)

Pinned stock `DarknessII.exe` SHA256: `D46BB6CB762732B72AB9D34428237D2AFA89F5792BDBED957D78793EE8134EC1`. Static addresses below are image VAs. No installed game file was modified for this audit.

## Confirmed producers

- Extracted scripts `D2/Scripts/CameraShake.lua` and `Audio/DarknessVoice.lua` write `postProcess.viewShake.mShakeAmbient` repeatedly.
- `Player/Stoned.lua` writes ambient, dampening, position/rotation factors, speed and sway fields. `PostProcess/DrunkWalk.lua` writes ambient, rotation factors and speed.
- Registered `mShakeAmbient` setter at `00DC8F50` resolves the script target via `00DADA80` and writes a float at object `+0x2C` (`00DC8FFC`); getter `00DC9030` reads the same field (`00DC90AA`). These functions cover one script property, not all native camera motion.

## Native candidates and limits

- The executable also contains named parameters `mCameraShakeStrength`, `mPlayerShakeStrength`, `mRunShake`, `mWalkShake`, `mImpactShake`, `mFallScreenShakeScaling`, `mRecoilStrength`, `mFPEntityIgnoresShakeTranslationAndRotation` and others. Their names do not establish a shared camera transform or safe live offsets.
- One contiguous reflected property group at `010B53C4..010B540C` names `mWalkShake` (walking noise), `mJogShake` (jogging noise), `mRunShake` (running noise), `mImpactShake` (impacts), `mZoomShake`, `mRumbleShake`, and `mViewShake` (camera shake params). This gives a more focused native parameter family. The group is metadata, not a writable live object or a common consumer; the layout/owner and animation order remain unresolved.
- The `mFPEntityIgnoresShakeTranslationAndRotation` name at `00FB8900` is a property metadata reference at `010B534C`, beside its description at `010B5350`. It does not identify an owned live first-person entity or an effective on/off value.
- A read-only scan for scalar loads at offsets `+0x2C`, `+0x34`, `+0x44`, `+0x48` found a cluster at `008D2662..008D2715`. It interpolates many fields between two objects, so it is not established as the camera-shake producer. `0066BC76..0066BD24` copies matrix rows; `00BAD219..00BAD260` reads camera-like parameters, but neither has proven `viewShake` ownership.

## Candidate gate

Identify the live owner and the native transform application order for camera, first-person arms, and gun. Suppress shake upstream of all three; preserve look, locomotion, aiming, recoil feedback that does not move the head, and cinematic transitions. A camera-only correction is excluded because it could leave the hands and weapon oscillating against a still scene. No shake-disable patch is ready or installed.

## Read-only selected-owner trace

The protected selected-player path already verifies the camera, avatar and parent model links. A gated `Diagnostics/CameraShakeTrace` observer reads the camera matrix at `camera+0x80` and the avatar parent world matrix at `parent+0x140` on that render path, at most every 50 ms for the first 30 gameplay seconds. It logs both forward vectors and positions with frame/time and the OpenXR head reference. The parent identity is pinned to the existing `00FFC300` class check used by the protected human-hand packer. This establishes a matched transform comparison during a repeatable shot/impact without writing either native matrix. It cannot itself prove the specific shake source or remove the effect.

## Headset trace: sprint and heart consumption

The user ran and ate hearts with the trace DLL installed. The log contains 478 selected-camera/root samples over 29.954 seconds. At 21–22 seconds, the avatar root traveled 4.14–4.29 game units per second and the camera/root position gap peaked at 0.070 units. At 26–28 seconds the root was almost stationary and the camera/root forward vectors diverged by up to 13.5 degrees, while the position gap returned to 0.018 units. The user described the visible shake as moderate. The log has no native event marker, so assigning the second period specifically to the heart animation is an inference. Neither period proves that an independent shake was applied to hands or weapon. The existing trace stops after 30 seconds and did not observe a distinct impact event.

Static examination of the selected camera vtable `00FFC7C0` identified slot 40 (`007AAB00`) as a plain 64-byte matrix setter writing to camera `+0x80`, and slot 39 (`00504810`) as the matrix getter. The setter has no direct `call` references in the executable; it is called through the vtable. It is a downstream transform sink, not a proven shared shake producer, so suppressing its input would risk changing legitimate look and animation.

The next read-only candidate samples the selected camera together with the native left/right wrist and weapon-grip bones in the protected human packer, after restoring any of our prior IK edits and before applying new controller IK. Each bone is transformed through the pinned avatar parent world matrix. This gives same-frame camera/arm evidence during movement and heart animation without changing gameplay transforms. It still needs a headset sample and source attribution before shake suppression.

## Second headset trace and bounded procedural candidate

The user performed sprint, heart consumption, sprint and tentacle waving. The installed hand trace yielded 479 camera/root and 479 native hand/weapon-grip samples over 30 seconds. During one running segment (9–11 seconds), root displacement was about 6.7–6.9 game units per second, and the camera/root translation gap peaked at 0.258 units. At 19 seconds, camera/root separation stayed near 0.022 units while the native wrist-to-camera distances changed 0.29–0.33 units: first-person animation can move hands independently of camera shake. One sample at 14.422 seconds had 29.8 degrees camera/root heading separation but returned near alignment within 63 ms; do not treat this isolated spike as a stable shake amplitude. The log lacks exact event markers for the four user actions.

Static dataflow on the pinned EXE identifies `00628420` as a procedural-noise generator. Its output is an aligned 16-byte vector at the receiver base plus scalar outputs at `+0x38..+0x40`; the routine also advances phase and amplitude state. It has exactly six direct calls: `0063187E`, `006318AC`, `006318CA`, `0063197B` inside the first-person update and `0076C86F`, `0076C892` in a separate camera-like update. The first-person caller combines the first three generated vectors into `this+0x1F0`/`this+0x20C` before additional view processing. The fourth generator is added later; the two `0076C8xx` calls are excluded from the first candidate because their owner is separate. The property loader at `004B2F60..004B3420` reads reflected `mWalkShake`/`mJogShake`/`mRunShake`/`mImpactShake`/`mZoomShake`/`mRumbleShake` settings into related `this+0x8C0`, `+0x910`, `+0x960` and neighboring blocks. These relationships support a procedural shake trial, while the full camera/hand composition is still a physical validation gate.

An opt-in `Diagnostics/CameraShakeSuppress=1` candidate redirects only the four pinned `006318xx/0063197B` calls. It executes the original generator, then zeros its four-float output and three scalar outputs. Phase, amplitudes and all other update work remain native. The exact stock EXE bytes, all four original call instructions and the generator prologue are checked before any patch; partial installation restores all altered sites. The default is OFF. This may leave other camera shake sources active and has no headset result yet.

The trial was installed, but the protected profile refused native EXE patches (`BlockNativeImagePatches=1`, `RestoreTrackedGameplay=0`). The log shows `CameraShakeSuppress requested=1` and `NativeImageGuard enabled`, with no `active=1`. The user still saw camera shake. All nine protected files were restored and independently matched the prior hashes. The hook source was removed from the active branch; commit `d1ed1aa9` remains as rejected evidence. This is not a test of whether zeroing `00628420` would affect shake; the intervention never ran. A future candidate must operate through verified, selected heap ownership while preserving camera/hand/weapon ordering.

Static ownership lead: the updater containing `0063187E..0063197B` starts at `00631470`. It is vtable entry `00FDF1CC`, and the settings loader `004B2F60` is entry `00FDF1A0` of the same table beginning at `00FDF170`. Constructor `00C410F0` writes `00FDF170` to its receiver. The selected-avatar observer has not yet confirmed that this table belongs to its live avatar. A read-only extension to `CameraShakeTrace` logs that selected avatar's actual vtable and, only when it equals `00FDF170`, the noise vectors at `+0x8C0`, `+0x910`, `+0x960`, `+0xCA0` and accumulators at `+0x1F0` and `+0x20C`. This is a bounded owner test, not a write or a claim that these fields alone control all shake.

The next headset log showed the selected avatar's actual table is `01001630`, so the first guessed direct identity was false; no field sampling in that DLL was admitted. A subsequent one-shot read-only scan of the same SHA-pinned game process examined 474 MB of committed private memory and found two `01001630` avatar instances, five `00FDF170` objects and one static-table camera. Both avatar instances had `avatar+0x5E0` pointing to the same reference wrapper, whose first word pointed to the same `00FDF170` object. This is evidence for a shared live shake/settings owner reachable from the selected avatar class, but the exact selected avatar pointer and mutation lifetime still need proof. At rest, the owner noise outputs at `+0x8C0`, `+0x910`, `+0x960`, `+0xCA0` were zero; neighboring frequency/scale fields were nonzero. A 10-second read-only action sample is prepared to identify which strength/output fields change during visible shake. The scan does not write process memory or install a debugger.

## Heap-only factor candidate (2026-11-01, evening)

Static read of the pinned EXE resolves the shake-parameter struct by its reflected names (loader `00B2EEE0`, name records `010A38F4..010A393C`): `+0x10..+0x18` `mShakeFactorRot`, `+0x24` `mShakeFactorPos`, `+0x28` `mShakeSpeed`, `+0x2C` `mShakeAmbient`, `+0x34` `mShakeDampening`. The owner loader `004B2F60` fills `+0x8C0` from `mViewShake`, `+0x910` from `mRumbleShake`, `+0x960` from `mZoomShake`, and the separate spring object `+0x1170` from `mImpactShake`; `mRunShake`/`mJogShake` go to scalars `+0xB84`/`+0xB88`.

Generator `00628420`: amplitude = `+0x20` (impulse, decays by `+0x34`) + `+0x2C` (ambient) + `+0x30` (movement, rewritten each update at `0063238E` from run/jog). Below a threshold all outputs are zeroed; otherwise rotation outputs `+0x38/+0x3C/+0x40` are noise x amplitude x `+0x10/+0x14/+0x18`, and the position vector `+0x00` is noise x amplitude x `+0x24`. Within the owner vtable only slot 23 (`00631470`, amplitudes `+0x8EC`, `+0x8F0`) and slot 27 (`00C8ABD0`, impulses `+0x8E0`, `+0x930`, or spring `+0x1170`) write these blocks; no method writes the factor fields. Amplitudes are therefore dynamic, factors are load-time settings.

Candidate `Diagnostics/CameraShakeSuppressHeap` (default OFF): on the render thread after `CaptureNativeGameplay`, verify avatar table `01001630`, follow `+0x5E0` to an owner with table `00FDF170` outside the image, then zero the 16 factor floats of blocks `8C0/910/960/CA0`. The scripted `mShakeAmbient` writes land in the view block's `+0x2C` and are silenced by the same factors. No EXE byte changes, so `BlockNativeImagePatches=1` stays valid. The log reports `refills` (native code restoring a factor), `proceduralMax` (must read 0 while `nativeAmplitudeMax` can stay nonzero, proving the generator still runs), and the untouched impact spring outputs `+0x1170+0x180/+0x190`. Headset result NOT RUN.

## Heap candidate result and animation-camera diagnosis (2026-11-01, 19:50)

Headset run with `CameraShakeSuppressHeap=1`: `ACTIVE=1`, 2602 writes, 0 refills, 0 refusals, yet amplitudes, outputs, impact springs and the `+0x1F0/+0x20C` accumulators of the reached `00FDF170` owner were exactly zero for 30 s of running and tentacle use. That owner is idle; rejected (see FAILED-APPROACHES). User: shake only while running, tentacle attacks and other hero/tentacle animations, not when standing still.

Same-run trace: the avatar parent matrix `parent+0x140` already carries look yaw and pitch (forward y follows camera pitch, e.g. -0.071 vs -0.070) and matches the camera within ~0.1 deg at rest; while running the camera moves up to ~0.1 units relative to it, and 1-4 deg during attack animations. The visible shake is the first-person animation driving `camera+0x80`.

Candidate `Diagnostics/CameraAnimStabilize` (`src/camera_anim_stabilizer.inl`, default OFF): C_stab = parent orientation (orthonormalised, native row scale) + camera offset in parent axes averaged over 1.5 s. The view head delta becomes `(C_anim * C_stab^-1) * H` (row vectors, view = C^-1, the same base the hand/gun `local * C` composition assumes), and hands, gun model, shot ray and throw ray use C_stab. Correction fades out above 0.5-1.0 units or 20-35 deg and during cinematics. Log `[CameraStabilize]` reports removed position/angle (counter-prediction: ~0 when still). Headset result NOT RUN.
